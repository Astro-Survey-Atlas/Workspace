Astro Survey Atlas / user workspace

Workspace (Atlas)

Workspace is the user-facing interactive data exploration surface in Astro Survey Atlas. It hosts the Aladin sky dashboard, local user-asset registration, connectors and credentials, local scanning with MOC Core, optional Warehouse remote scans, and a read-only MCP surface over user data. Public survey geometry comes from Assets Resource Package v3 (one-way consume). High-throughput remote scans can be delegated to Warehouse when configured.

Assets

public Resource Package v3

Workspace

viewer + user assets + MCP

Warehouse

optional remote ScanRequest

MOC Core

geometry kernel

Explore the sky

Aladin Lite v3 viewer with ICRS coverage, density, objects, and display-only survey layers from installed public packages and user scans.

Own user data

Register private assets and connectors, run local CSV scans, keep Workspace Elasticsearch and user MOC artifacts independent of Warehouse.

Stay deterministic

Parsing, HEALPix indexing, and MOC generation run in tested code via pinned MOC Core. MCP and Agent adapt that plane; they do not invent geometry.

02 / Boundary

Product boundary

Taken from the in-repo architecture and atlas-boundary plan. Atlas owns user-side state; it does not become a public survey catalog.

Workspace owns

  • User assets, local survey/release labels, connectors, and access metadata
  • Local scanning and optional remote user scans through Warehouse
  • Its own Elasticsearch search indexes, sky coverage queries, and the viewer
  • User MOC artifacts, scan/task history, and evidence references
  • Deterministic Agent/MCP and workflow runs over user data

Workspace does not own

  • Public survey jobs, public connectors, MOC publication, or a public release catalog
  • Registering a user asset with Assets, or publishing user records back to Assets
  • Warehouse Elasticsearch as a shared database (Workspace ES stays independent)
  • Warehouse scanner/operator runtime or Assets management APIs

Ordinary public geometry comes from the immutable Resource Package v3 published by Assets. Fine-grained public region queries, when used, stay server-side and scoped—browsers do not hold Assets credentials. Atlas never stores the complete public tile/file/shard index.

surveyId and releaseId on user assets and connectors are Atlas-local labels. A matching public package record is never required for a user registration. HTTP namespaces stay separate: /api/surveys addresses Atlas-local labels; /api/public-surveys reads installed Resource Package v3 metadata for the public viewer only.

03 / Viewer

Sky viewer

The frontend viewer (Vite + TypeScript + Aladin Lite v3) is the authoritative celestial explorer for Atlas. One ICRS sky contract drives coverage, density, objects, and survey layers.

Representation Purpose Source
Coverage Show where public or user data exists Assets package or user scan projection
Density Compare occupied regions Nested HEALPix counts
Objects Inspect rows Valid user-source coordinates (local index)
Survey layers Compare public packages and user assets Display-only shell offsets

Shell offsets are visual layout only—they never represent distance, depth, wavelength, magnitude, or completeness. Region selection and Aladin exploration operate on the same public/user layer set. Geometric overlap (POST /api/sky/overlap) intersects visible public and workspace sources that already have pixel evidence; ordinary geometry overlap does not require a file reverse-lookup index.

Coverage ≠ download. A verified public MOC means the survey recognizes the region. It does not guarantee that corresponding science files are readable or downloadable. Availability states (geometry-only, entrypoint-only, candidate/incomplete, tile-resolved, unavailable) stay distinct in overlap and download-plan flows.

04 / Assets

User asset registry

Workspace is the authoritative owner of private data assets. Add, inspect, filter, edit, and delete user assets with normalized survey/release labels—catalog, image, spectrum, cube, timeseries, and related modalities as registered locally.

  • Local labels only. User surveyId/releaseId/product never write back to Assets and need not exist in the public package catalog.
  • Status is derived. GET /api/data-assets/status reports coverage (not_started / pending / failed / ready / empty / unavailable), object indexability, and a suggested next action. Registration alone (“acquired”) is not sky coverage.
  • Only ready MOCs draw. Pixels appear on user sky layers when coverage is ready; a pending or failed latest scan keeps the previous ready artifact visible when one exists.

05 / Connectors

Connectors

Register data sources and run structural connection checks. Credentials stay in the managed secret store—never in asset metadata, ScanRequest bodies, evidence, or HTTP responses.

local

Local filesystem

Controlled read-only connector root. Local CSV scans write objects and coverage to Workspace Elasticsearch and generate user MOC artifacts.

s3

S3-compatible & Ali OSS

Amazon S3 and Aliyun OSS endpoints (OSS handled through the s3 connector kind with the Ali OSS SDK when the hostname matches). Used for connection checks and optional Warehouse remote scans.

jdbc

JDBC databases

Workspace connectors include JDBC for structural checks and Workspace-side use. Warehouse ScanPlan v2 does not yet accept JDBC sources—remote Warehouse scans remain local/S3/OSS only.

check

Connection tests

POST /api/connectors/:id/check validates endpoint, bucket, prefix, or database connectivity. A successful check is not scan-completion evidence.

06 / Local scan

Local scan & user MOCs

The deterministic local scanner parses CSV under a local connector, validates RA/Dec, builds nested HEALPix indexes, and generates IVOA FITS MOC files through the pinned astro_survey_moc_core adapter.

Local path

POST /api/connectors/{id}/local-scan (or asset-scoped local scan). Writes Workspace ES + user MOC store. Incomplete local scans are marked failed on restart—never exposed as ready coverage.

MOC Core contract

Normal output: ICRS, NESTED, IVOA FITS MOC, maxOrder=10; query order 8 and preview order 4 derived from the authoritative MOC. Empty or invalid inputs stay metadata-only or failed—no footprint inferred from a filename or survey label.

User MOC artifacts

At least moc.fits, query-order8.json, preview-order4.json, and SHA-256. /api/user-mocs returns metadata; allowlisted artifact downloads only. /api/sky/coverage merges ready user layers with public packages.

Supported user coverage modes include catalog-radec (object presence), nested-healpix, and fits-wcs (image extent). Coverage role, data origin, source tier, version, and SHA-256 stay attached to the stored coverage record. Public publication of user MOCs is outside Atlas.

07 / Warehouse

Optional Warehouse remote scans

When Warehouse is enabled, Workspace submits a namespaced ScanRequest with ScanPlan version 2 for one bounded S3/OSS source, polls status, reads only Warehouse ast_* indices, and imports evidence into Workspace for MOC generation.

  • Optional. With Warehouse disabled or unavailable, Workspace still starts, serves user assets, local scans, installed public packages, and existing user MOCs. Remote submit returns an explicit disabled/unavailable error.
  • Tracking labels. Requests use track-caller=workspace and track-task-kind=user-scan|user-coverage (plus asset/connector/batch ids). History APIs return only Workspace-owned records.
  • Two Elasticsearch planes. Workspace: astro_*_index_v1 via ASTRO_ES_URL. Warehouse: ast_*_index_v1 via ASTRO_WAREHOUSE_ES_URL. Neither is a fallback for the other.
  • No remote object rows (v1). Warehouse evidence yields file/coverage cells and user MOCs—not per-row catalog objects. Object-level exploration needs a local scan into astro_object_index_v1.

Details for ScanPlan fields and Operator behavior live in Warehouse docs. Workspace HTTP contracts for remote submit and history are summarized in the repo docs/api-reference.md.

08 / Public packages

Resource Package v3 consume

Public geometry is a one-way consume path. Workspace downloads, validates, and activates Assets-published immutable v3 packages. It never writes user records or user MOCs back to Assets.

  1. Fetch and validate the Assets v3 catalog.
  2. Keep the verified catalog under assets-snapshots/<hash>/ and atomically expose assets-current.
  3. Download packages on demand; verify archive size and SHA-256; validate every v3 manifest and FITS MOC.
  4. Activate selected release layers for the read-only public sky view.

If Assets is unavailable, a previously verified local snapshot remains usable. With no successful snapshot, public resource endpoints return 503; user assets, local scans, indexes, and task history continue. Atlas does not scan bootstrap catalogs, parse v1/v2 packages, or keep a second public footprint generator.

Scoped reverse lookup (when configured). Explicit overlap-detail or download-plan sessions may call a bounded, authenticated Assets query from the Workspace server. Results are region-scoped with revision/expiry; the browser never receives the credential. Geometry-only layers can still display and participate in overlap without creating executable download items.

09 / Agent

Agent & MCP

MCP and the Agent are adapters over the deterministic data plane. They select tools and interpret results; they do not implement a second WCS, HEALPix, or MOC algorithm.

  • MCP server (asa-workspace): read-only tools over Atlas-owned user assets—currently list_user_assets and get_user_asset. Public Assets packages are not included.
  • ToolRegistry / WorkflowRegistry: validate deterministic tool contracts and versioned DAGs. Example: Euclid × DESI cross-match workflow over the configured catalog MCP client—an Atlas workflow, not a public coverage builder and not a publisher to Assets.
  • Agent intent remains rule-based until an explicitly configured LLM integration is enabled.

A global notification deck (#workspace-notification-deck) reports temporary progress for package sync, connector checks, scans, and errors with a single unified lifecycle.

10 / Run locally

Quick start

Pointers from the repository README. Prefer the README and chart docs for full deployment contracts.

Prerequisites

  • Node.js >= 22.13
  • Python 3.10+ (MOC Core CLI wheel)
  • Elasticsearch 8.x (Workspace-owned search plane)
  • SQLite (default) or PostgreSQL
Local development
npm ci
npm run build

# Terminal 1 — API on 127.0.0.1:3000
npm run dev

# Terminal 2 — Vite viewer (proxies /api)
npm run dev:viewer
# Open http://localhost:5173

Other run paths

  • Docker Compose (release image): docker compose -f compose.release.yaml up -d then curl http://127.0.0.1:8080/healthz.
  • Helm: chart charts/asa-workspace on GHCR OCI; see chart README for metadata-store and search modes.
  • Windows desktop installer: GitHub Releases setup.exe bundles API, viewer, and embedded Python/MOC Core; first launch configures data directory and Elasticsearch (external or Docker-managed).

Validate with npm test, npm run test:e2e, or npm run validate. Full steps: README.md.

11 / Honesty

Limits & non-goals

This Pages site documents landed Workspace capabilities only. The following are explicitly out of scope or not claimed here.

  • No public catalog ownership. Assets owns public survey/release/product publication; Workspace consumes packages.
  • No science-array proxy. Workspace does not claim to stream or proxy arbitrary FITS/science arrays as a general file server. Bounded coverage-download jobs (when configured) verify and register concrete public source units into a new local connector—they are not a substitute for survey archives.
  • No depth maps. FITS MOC expresses where data exists, not sensitivity or quality. Depth layers are not inferred.
  • No TAP/SIA / sky-footprint-mapper / cosmos-explorer-ui claims unless and until those land in current repo docs as implemented Workspace features.
  • No write-back to Assets. User assets, user MOCs, and user task history never register or publish into Assets.
  • No shared ES with Warehouse. Two independent search planes; Warehouse outage must not block Workspace startup.
  • Remote scans ≠ object catalog. Warehouse v1 evidence is file/coverage/MOC, not per-row objects.
